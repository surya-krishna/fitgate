# Health & safety model

FitGate asks people to exercise. Some of those people have heart conditions, joint injuries, or are pregnant. This document is the contract for how the project handles that. Changes here need a maintainer review.

## Principles

1. **The LLM proposes. Rules constrain. A clinician disposes.** No plan generated by a model becomes active without passing a deterministic safety envelope *and* a human review.
2. **Health data never leaves the server.** Devices receive task labels, reps and rules — nothing about why. The gate UI never shows conditions. Telemetry events carry task kind and outcome only.
3. **Fail open, never fail hurt.** If in doubt the daemon passes the gate. If a plan is missing, paused, or unreviewed, the built-in pool (bodyweight, low-impact, restorative) is used — or nothing, if the user disabled it.
4. **Self-report is trusted.** Nobody is punished for pressing Skip. Streaks reward completion; nothing shames non-completion. (Wearable confirmation is a roadmap item and will stay optional.)

## The pipeline

```
HealthProfile ──▶ deriveConstraints()  ──▶  LLM draft (structured output)
 (PAR-Q+ screen,     deterministic:            inside the constraints
  conditions,        allowed kinds,                    │
  meds, injuries,    max intensity,                    ▼
  level, age)        max reps/seconds        enforceConstraints()
                                              removes/clamps anything
                                              outside the envelope
                                                       │
                                                       ▼
                                             plan.status = pending_review
                                                       │
                   user shares /review/<token> ────────▶ clinician approves,
                                                        edits, or requests changes
                                                       │
                                             plan.status = reviewed
                                                       │
                                   user reads + accepts ▶ active ▶ synced to devices
```

### Screening (PAR-Q+ derived)

Eight yes/no questions in `HealthProfile.screening`. Any *yes* is a red flag:

* the envelope drops to **restorative only** (stretching, walking, breathing, eye rest, hydration, posture);
* strength and impact kinds are removed regardless of what the model outputs;
* the plan is labelled as red-flag-restricted in `safetyNotes` for the clinician.

Additional deterministic rules (see `packages/llm/src/plan.ts`):

| Profile signal | Effect |
|---|---|
| sedentary | light intensity, ≤10 reps, ≤60 s |
| beginner | light intensity, ≤15 reps, ≤90 s |
| advanced | ≤30 reps, ≤180 s, moderate allowed |
| joint problem worsened by activity | no jumping jacks, high knees, stairs, lunges |
| pregnant / postpartum | no plank, push-ups, jumping jacks, high knees |
| age ≥ 65 | light intensity; no impact kinds |

Rules are intentionally conservative. Loosening them is a clinician's job, per patient, on the review page.

### Clinician review

* The review link is a single-use token with a 14-day expiry. It shows the plan **and** a summary of the health profile — the one place the profile is shown to a third party, with a banner stating the patient shared it intentionally.
* The reviewer can approve as-is, edit reps/seconds, remove tasks, add contraindications, or request changes with notes.
* Reviewer name and credentials are stored with the decision. FitGate does not verify licences; the user chooses whom to trust. Hosted deployments in regulated markets should add verification before offering "find a reviewer" features.

### After activation

* Users may tune reps/seconds within **±25 %** of the clinician-approved values and change pacing rules freely.
* Removing tasks or increasing volume beyond +25 % sends the plan back to `pending_review` and the dashboard says why.
* Plan versions and reviews are immutable rows; the audit trail is the point.

## What FitGate is not

* Not a medical device, not diagnosis, not treatment. The onboarding consent and the landing page say so plainly.
* Not a surveillance tool. There is no manager view of an individual's health profile, and team features (roadmap) will aggregate only completion counts.

## Reporting a safety issue

If a generated plan contained something dangerous, open an issue with the label `safety` and include the `safetyNotes` and `enforcementChanges` from the plan (never the profile). Safety issues are triaged before features.
